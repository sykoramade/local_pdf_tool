03
Design direction — trust as the visual language
◈
The single most important design principle
Trust is not communicated by words. It's communicated by what the visual language, the proof elements, and the product name all say before anyone reads a single sentence. "PDFNoLimit" currently signals the same category as the tools it's competing against. The architecture deserves better representation.
Visual language: institutional restraint
Dark navy or deep slate background on the hero — not startup blue, not tech teal. This reads as "serious software" to the professional audiences we're targeting. White space is generous. Typography is editorial. No shield icons, no padlock animations — those are so overused they signal insecurity rather than security. The palette should feel like a financial institution or a law firm's web presence: calm, precise, unhurried.
The proof element: DevTools, not badges
The highest-trust element on the landing page is not an ISO badge. It's a DevTools Network tab showing zero requests during document processing. This is an auditable, verifiable claim — not a marketing assertion. Place it prominently above the fold. It tells a technically literate person "this tool is making a claim it can prove, not a promise you can't verify." For non-technical visitors, the caption does the work: "0 network requests — your file never left this tab."
Name recommendation
"PDFNoLimit" positions the product as competing on quantity/paywall removal — which is half the story. The privacy angle is the differentiating claim and should be in the name or tagline. Suggestions: LocalPDF (exact match to the repo name, descriptive, honest), VaultDraft, Clearform, Folio, Privadoc. The name should answer "what does it do differently" in one word. LocalPDF is the strongest because it literally describes the architecture.
Above-the-fold hierarchy
1. The claim: "Edit, sign, and annotate PDFs. Your file never leaves this browser."
2. The proof: DevTools network tab (zero requests)
3. The CTA: "Open a PDF — no account needed"
4. The secondary CTA: "How to verify this yourself →"
5. Trust bar: No upload · No account · EU-built · Open source

Features come below the fold. Certifications come below features. The conversion logic: trust earns the click, features justify the upgrade.

Bug
S9-3
Fix: Undo state freeze
After pressing undo, the editor becomes non-interactive. Debug the undo state manager — likely a stale ref or broken history stack. After undo, all text items must remain clickable and editable. Add a regression test case: edit → undo → re-edit the same item.
Bug
S9-4
Fix: Bold text bleeding to adjacent paragraphs
Editing a text item that begins with bold causes adjacent text blocks to inherit bold styling. Root cause: style state not scoped per text item. Each text item must maintain its own independent style state. See lessons-learned.md — bold preservation is noted as a known gap.
Bug
S9-5
Fix: Main thread block during PDF save
PDF save/download freezes the browser UI. Move the pdf-lib serialisation to a Web Worker. The worker receives the document data, processes it off the main thread, and posts the result back. This also improves performance on large documents. See lessons-learned.md: setTimeout for DOM sync is wrong — use proper worker message passing.
Bug
S9-6
Fix: French PDF encoding bug ("r" → "rv")
PDFs with French content produce extra characters during text extraction. Root cause: ligature or encoding mapping issue in the text stream parser. Specifically investigate ToUnicode CMap handling for PDFs using Windows-1252 or custom encoding. French PDFs use ligature glyphs (fi, fl, ff) that some CMap tables map incorrectly.
Bug
S9-7
Fix: Font regression from recent update
A recent push broke font rendering on previously working PDFs — unedited text rendering as sans-serif on download. Bisect the recent commit history to find the change. Likely a font embedding or fallback change in save.ts or the text layer. Restore the previous behaviour for unedited text items.

Font architecture — the decision and the message
The font server is currently the only thing preventing a clean "zero network requests during document processing" claim — which is the single most important trust proof the product has. The question isn't whether to fix it, but how. Three options were evaluated; one is clearly correct.
◈
Why this decision is load-bearing for the entire product strategy
Every landing page, every trust badge, every "verify it yourself in DevTools" CTA, every healthcare/legal/government audience pitch — all of it depends on the network tab staying silent while a document is processed. If the font server is sending anything during an active editing session, the core claim is compromised. This is architectural, not cosmetic.
—
The three options evaluated
Recommended · 9/10
Option A — Full local font bundle
Confidence: 9/10
Curate a pack of ~18 fonts covering 95%+ of real-world PDFs. Lazy-load them from your own Vercel CDN edge on first use, cache in IndexedDB, and never request them again. Implementation note: fonts should be hosted on your own Vercel CDN, not pulled from Google Fonts. Google Fonts would log the request (and the IP address making it), which creates a privacy optic problem even if no document content is involved. Self-host the font files at /fonts/[fontname]-[weight].woff2 and serve them with aggressive cache headers (max-age=31536000, immutable). A user who edits a PDF with Calibri on Tuesday will load that font once and never request it again.

Backend
3
resolveFont(fontName) — detect, fetch, cache
Normalise the font name from the PDF (lowercase, strip suffixes, strip spaces). Check IndexedDB cache first. If miss: fetch from /fonts/, store in IndexedDB keyed by font name, return ArrayBuffer. If not in pack: return null (triggers graceful fallback). The cache means a return user editing any Calibri document never makes a font request.
export async function resolveFont( rawFontName: string ): Promise<ArrayBuffer | null> { const key = normaliseFontName(rawFontName) const cached = await fontCache.get(key) if (cached) return cached const url = FONT_PACK[key] if (!url) return null // graceful fallback const buf = await fetch(url).then(r => r.arrayBuffer()) await fontCache.set(key, buf) return buf }
Backend

Font match indicator in the editor UI
Show a small status indicator per text item: "Font: Calibri · Exact match" (green) or "Font: SomeCorpFont · Closest: Arial" (amber with tooltip). This transparency is a trust signal, not a liability — it shows the user exactly what the tool found and what it used. It also pre-empts the support ticket "my font looks slightly different."

How to message the font architecture — copy for landing pages
The font architecture is actually a feature story, not just a technical detail. Most PDF editors either destroy fonts (replace everything with Arial) or upload your document to match fonts server-side. You do neither. Once Option A is built, you have a genuinely differentiated claim about font handling that no other free tool can make. Here is how to message it at each level of the page.
Homepage hero — one line, maximum trust signal
Use under the headline or in the trust bar
"Font matching runs locally. Your document never leaves your browser — not even to identify your fonts."
This is the sharpest possible version of the claim. It proactively answers the skeptic who thinks "but font detection must phone home." It doesn't require the user to know what a font server is — it just reassures them that even the technical parts happen locally.
Feature section — one paragraph explaining how it works
Font matching that doesn't read your document
"Most PDF tools match fonts by uploading your document to a server. LocalPDF detects the fonts in your PDF, finds the closest match from a locally cached library, and applies your edit — without sending a single byte of your content anywhere. The font files live in your browser cache after the first load. After that, even the fonts load locally."
This paragraph is also an SEO asset — it answers "how does pdf font matching work without uploading" which is a real search query from technically curious users who are exactly your target audience.
